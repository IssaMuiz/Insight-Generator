# Embedding

## Overview

The embedding component converts each text chunk produced by the chunking stage into a numerical vector representation using a Sentence Transformer model.

These vectors are required later for semantic search and retrieval in the RAG pipeline.

The embedding stage sits here:

PDF
→ Parser
→ Cleaner
→ Chunker
→ Embedding
→ Vector Store
→ Retrieval
→ LLM

---

## Purpose

The purpose of the embedding component is to transform chunked book text into vector representations that capture semantic meaning.

For example:

"This is a short text"

is converted into a numerical vector such as:

[0.12, -0.04, 0.31, ...]

The actual vector contains many dimensions; the values are generated by the embedding model.

Each generated vector remains associated with its original `TextChunk`.

---

## Model

The project uses:

`BAAI/bge-small-en-v1.5`

through the Sentence Transformers library.

The model is loaded when a `TextEmbedding` instance is created.

The model name can also be supplied explicitly, allowing the embedding model to be changed later without changing the rest of the pipeline.

Example:

`TextEmbedding(model_name="BAAI/bge-small-en-v1.5")`

---

## Data Model

The embedding result is represented by `TextEmbed`.

Conceptually:

TextEmbed
├── chunk
│ └── TextChunk
└── embedding
└── list[float]

The original `TextChunk` is preserved instead of copying its individual metadata fields into the embedding object.

This keeps the relationship between the vector and its source text explicit.

The original chunk provides information such as:

- chunk ID
- text
- page number
- chunk index
- word count

This metadata will be useful later when retrieval returns a relevant vector and the system needs to identify the source passage.

---

## Embedding Process

The `embed()` method accepts:

`list[TextChunk]`

The process is:

1. Extract the text from every chunk.
2. Send the complete list of texts to `SentenceTransformer.encode()`.
3. Encode the texts in batches.
4. Normalise the embeddings.
5. Pair each generated embedding with its original `TextChunk`.
6. Create a `TextEmbed` object for each pair.
7. Return the complete list.

The model is called once for the entire collection rather than once per chunk.

This approach avoids unnecessary repeated model calls and allows Sentence Transformers to process the chunks in batches.

---

## Batch Configuration

The current embedding configuration is:

- `batch_size=32`
- `show_progress_bar=True`
- `normalize_embeddings=True`

`batch_size=32` allows multiple chunks to be processed together.

`normalize_embeddings=True` produces normalised vectors, which is useful for similarity-based retrieval.

The progress bar is enabled so that processing a large book provides visible feedback.

---

## Empty Input Behaviour

When `embed()` receives an empty list:

`[]`

it immediately returns:

`[]`

The embedding model is not called.

This avoids unnecessary work and gives the method a clear contract for empty input.

---

## Type Conversion

Sentence Transformers returns embedding vectors in a NumPy-based representation.

The application converts each vector to a Python list before storing it in `TextEmbed`.

Therefore the application-level representation is:

`list[float]`

This matches the type declared by the `TextEmbed` data model.

It also provides a simpler representation for later serialisation and storage.

## Testing

The embedding component has both unit tests and an integration test.

### Unit tests

The unit tests mock `SentenceTransformer` so that tests do not load the real model.

They verify:

- the model is correctly stored
- the expected loading messages are printed
- the correct number of embedded chunks is returned
- original chunk information is preserved
- generated vectors are associated with the correct chunks
- `encode()` is called exactly once
- all chunk texts are passed to `encode()` together
- `batch_size=32` is used
- `show_progress_bar=True` is used
- `normalize_embeddings=True` is used
- empty input returns an empty list
- `encode()` is not called when there are no chunks

### Integration test

The integration test uses the real Sentence Transformer model rather than a mock.

It verifies that:

- the real model can be loaded
- real chunks can be embedded
- two input chunks produce two results
- the generated embeddings are Python lists
- source chunk metadata is preserved
- generated embeddings are non-empty

The integration test is intentionally separate from the unit tests because loading the real model is slower and depends on the local ML environment.

---

## Why Mocking Is Used

The Sentence Transformer model is an external dependency and can be expensive to initialise.

Unit tests therefore replace the real model with a mock.

The mock provides predictable embedding values such as:

[0.1, 0.2, 0.3]

This allows the tests to focus on the behaviour of the project's own embedding code rather than testing Sentence Transformers itself.

The integration test then verifies that the same code works with the real dependency.

## Current Design

The current architecture is:

TextChunk
↓
TextEmbedding.embed()
↓
extract chunk.text
↓
SentenceTransformer.encode()
↓
embedding vectors
↓
convert vectors to list[float]
↓
pair vectors with original TextChunk
↓
TextEmbed
↓
list[TextEmbed]

---

## Design Decisions

### One model call for many chunks

The entire chunk list is encoded together rather than making a separate model call for every chunk.

This makes the embedding process more efficient and is better suited to processing full books.

### Preserve the source chunk

The vector is stored together with its original `TextChunk`.

This makes it possible to trace a retrieved vector back to its source text and page.

### Keep embedding generation separate

Embedding generation is implemented as its own component rather than being mixed into chunking.

This keeps responsibilities separated:

Chunker
→ decides how text is divided.

Embedding
→ converts the resulting chunks into vector representations.

Vector store
→ will later handle storage and similarity search.

This separation makes each stage easier to test and replace.

---

## Current Limitations

The current implementation loads the embedding model when `TextEmbedding` is instantiated.

This is acceptable for the current development stage, but deployment may later require a more deliberate model lifecycle so that the model is loaded once and reused efficiently.

The current embedding configuration is also fixed in the implementation:

- batch size
- progress bar
- normalisation

These can be made configurable later if deployment or performance requirements justify it.

The current implementation also assumes English-language practical nonfiction books because the selected embedding model and current project scope are designed around this use case.

---

## Completion Criteria

The embedding stage is considered complete when:

- a list of `TextChunk` objects can be embedded
- the model is loaded successfully
- embeddings are generated in batches
- source chunks remain associated with their vectors
- embeddings are represented as `list[float]`
- empty input is handled safely
- unit tests pass without loading the real model
- the integration test succeeds with the real model

The embedding component has now met these requirements.
